Chapter 00

The demo DM-NAX starts

dmnax-server stands in for a real DM-NAX-4ZSA. Everything starts here: it builds a pretend device in memory, writes the settings file every client reads, and answers Media Player 2.0, REST and a status page on one TLS port.

Terminal 1python dmnax-server/server.pyoptions--port 8443 --players 5 --zones 5 --fault NAME --quiet
In AV termsIt is a bench processor with a loaded program: five media players, five zones, a fixed input table and a front-panel status page, plus switches to make it misbehave on purpose.
Chapter 01

Inside Media Player 2.0

Media Player 2.0 (MP2) is the DM-NAX's streaming player API: JSON over one secure WebSocket, wss://<device>/subscriptionmgr. Every request has the same wrapper, {"Device": {"<CommandSet>": {"RequestAction": {...}}}}, and replies and pushes come back shaped like the part of the device that changed. The messages below are real, captured from crestron/mp2.py talking to dmnax-server.

In AV termsRegister is like a panel joining the program; subscribe is like turning on feedback for a join. After that the device sends changes on its own, and a command only counts once the feedback says it happened.

The player's states and the actions it offers

Each push carries PlayerState and AvailableActions. Clients only send an action the player offers right now; anything else comes back as a refusal Notification. LoadSource is always accepted.

Chapter 02

DM-NAX REST: zones, volume and routing

The player is MP2; everything about rooms is REST, the DM-NAX's CresNext JSON over HTTPS. You log in once, read with GET, write with POST /Device. Nothing is pushed, so every write is checked by reading it back. Client code: crestron/rest.py; server side: dmnax-server/rest_api.py.

In AV termsLike sending a level to a DSP and then polling the level back, because this interface has no feedback channel. "OK" means accepted, not done.
Chapter 03

The Python demo: plan, then prove every step

demo_python/main.py runs a fixed script on Player01 and its zone, Kitchen, using chapters 01 and 02 underneath. It only reads until you allow a change, and each change passes only when the device shows it happened. Pick how you start it:

Terminal 3python demo_python/main.py --config dmnax-server/client-config.json --execute
Chapter 04

MCP over stdio: the device as tools

MCP (Model Context Protocol) lets a program, or an AI assistant such as Claude, list tools and call them with JSON-RPC. Both servers here offer the same 15 tools and approval rules from demo_mcp/protocol.py. demo_mcp reads and writes the JSON itself; demo_mcp_sdk hands that to the official MCP Python SDK. The JSON below is a real exchange with demo_mcp/server.py.

Terminal 3python demo_mcp/client.py --config dmnax-server/client-config.jsonorpython demo_mcp_sdk/client.py --config ...
In AV termsThe tools are a device driver's functions (play, set volume, route). The menu or the AI is the touch panel calling them, and every change except pause waits on a confirm button.

Chapter 05

MCP over HTTP: start once, connect by URL

Same tools, same approval; only the transport changes. With stdio the client starts the server. Here you start demo_mcp_http/server.py and any number of clients (up to 16) connect to http://127.0.0.1:8000/mcp, each in its own session. Headers and replies below are real.

Terminal 2python demo_mcp_http/server.py --config dmnax-server/client-config.jsonTerminal 3python demo_mcp_http/client.py
In AV termsLike moving from a serial cable to a control server on the network: the device logic stays put, clients connect when they need it, and the server keeps each connection's state apart.

Chapter 06

When things go wrong

dmnax-server can misbehave on purpose. Switch a fault on from the status page (https://127.0.0.1:8443/, under Fault injection), the API, or --fault NAME at start, then run any client. Pick a fault to trace it from the switch to the exact message you read. In an MCP menu the same text arrives as Tool <name> failed: {'error': '...'}, and a failed change adds The change may or may not have applied; read the state back.

Glossary

Words used on this page

MP2
Media Player 2.0: the DM-NAX streaming player's API, JSON over a secure WebSocket (wss://). It pushes changes to subscribers.
CrestronAuth-SHA256
MP2's login: an HMAC signature of the client id, GET, the URL, a time stamp and a one-time nonce, made with the client secret. The secret itself is never sent.
RcSessionId
The id RegisterClient returns. Every later MP2 request carries it.
Subscribe
SubscribeToObject: ask the device to push every change under a path, such as /Device/MediaPlayerNeXt/Players/Player01.
SignedData
A blob the device signs and attaches to every menu item. To open or play the item you send it back unchanged; an altered one is refused.
AvailableActions
The player actions allowed right now. Anything else is refused with a Notification.
Notification
How MP2 says no: a push with a Msg such as Set Station Failed: ....
REST
The DM-NAX's HTTPS API for zones, volume, mute and routing. You ask (GET) or change (POST); nothing is pushed.
XSRF token
CREST-XSRF-TOKEN, returned at login. Every REST write sends it back as X-CREST-XSRF-TOKEN.
ReservedPlayer
A zone's media-player input (Kitchen reserves Input05, which is Player01). That is how the demos find the zone for a player.
MCP
Model Context Protocol: a standard way for a program or AI assistant to list tools and call them.
JSON-RPC
MCP's message format: a request with a method and an id, and a reply with the same id. A message without an id is a notification and gets no reply.
stdio
Standard input and output: the two pipes between a program and the process that started it.
Approval token
One-time value from a change tool's preview call. Valid 120 seconds, for that tool and those exact arguments.
Elicitation
MCP feature where the server asks the user a question through the host, for example a yes or no form.
Mcp-Session-Id
HTTP header naming one client's session on the HTTP server.
SSE
Server-Sent Events: a long-lived HTTP reply the server keeps writing messages into.
